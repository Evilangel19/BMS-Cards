# Architecture - how the program is built now

What is checked, what is open and what is planned is in `ROADMAP.md`; the history of the changes is in the git log. The `dev` branch also keeps an archive (`docs/archive/`) with the old roadmap and architecture documents, the diary of every patch, which go further back than the git log. This file only says how things are today.

## Principles

- Portable: one folder (exe + `config.json` + optional `data/`), easy to move or delete. No installer, no automatic updater.
- Everything about the game is read from the user's own Falcon BMS installation. The repository contains **no BMS data** (test fixtures and golden results are gitignored: `tests/fixtures/`, `tests/golden/`, `app/js/data/local/`).
- Parsers are independent: file in, data out. Rules and calculations are pure functions without DOM. The UI is a separate layer.
- One rule for each thing: friend / foe in `core/coalitions.js`, the DTC groups (steerpoint ranges) in `core/mapdtc.js` (`GROUPS`), settings defaults in `config/config.js`.
- UI text is English. BMS file formats are followed byte for byte when a file is written (DTC `.ini`: CRLF, no BOM).

## Stack

Tauri v2 shell (`src-tauri/`, Rust: file access, folders, config) + a vanilla ES-module web app in `app/` (no bundler, no framework). Leaflet (map), pdf.js, html2canvas are in `app/vendor/` with their licences. The desktop program runs under a Content Security Policy (`src-tauri/tauri.conf.json`): its own scripts only, no inline script or handler, no `eval`; the permissions of the file plugin are in `src-tauri/capabilities/default.json` (writing only for the kinds of files the program makes, programs and scripts blocked). The same page also runs in a plain browser, with fallbacks (`platform/desktop.js`).

## Data flow

1. At start `app/js/app/gamedata.js` / `gamefiles.js` find the BMS folder (desktop app) and read the tables into `data/index.js` and `bmsdata/*`.
2. A campaign (`.cam`, `.uni`, `.tea`, `.iff`, `.l16`, weather `.fmap`, `.twx`) or a Tactical Engagement is opened in `app/js/app/campaign.js` and parsed by `parsers/`; `core/cam-core.js` ties the pieces together (flights, ATO, bullseye ...). The last choice wins: a campaign of the menu still loading is dropped when another one is chosen (the arrow keys choose at every step) or a campaign or a mission is opened another way (`CAMGEN`, `campCancel`, `loadCam(file, stale)`).
3. A flight is selected (`app/js/app/selection.js`): the Datacard (`core/fillcard.js`, `cardlayout.js`) and the other pages are filled from it.
4. The DTC (`.ini`) is opened as a list of lines (`parsers/dtc.js`); the Map and Weapons pages edit steerpoints, PPT, lines and weapon targets in it (`core/mapdtc.js`); saving writes it back and also the campaign / TE `.ini` like BMS does (short format). Before writing, the file on the disk is read: it is the original kept once in `backup\dtc`, and when it is not the one opened here (BMS saved it meanwhile, or the DTC came from a mission) the confirmation says so.
5. A mission file (`core/mission.js`) carries one package to a pilot without the campaign, but not without the game data (the tables of `data/index.js`: a mission is refused without them, like a campaign). A mission of another pilot brings only the DTC block (`DTC_BLOCK_SECS`, checked line by line like the edits): it goes into the pilot's own DTC (`<callsign>.ini` of the DTC folder, opened by itself); when no DTC is open a window waits: open the DTC, open the mission without the DTC data, or cancel. `msfLoad` returns true only when the mission was opened.
6. Kneeboard: the DDS files are written in the kneeboard folder; the originals are kept once for each folder in `backup\kneeboard` (`index.json` gives the sub-folder of each folder; the copies made before the index belong to the first folder that asks).

## Pilot seat (Datacard, DTC, MDC)

A card and its DTC are made for one pilot of the flight. `app/js/app/seat.js` holds the choice: `ST.SEAT = { n, set, ask, note }` (n = 0..3 the seat, -1 none: the values of the leader; set = chosen by the pilot, false = the default, the leader; ask = a mission of another pilot was opened and his name is not on it; note = why a seat was given up). The choice is global: it stays when another flight is chosen, and a flight that has not that aircraft makes the card neutral (with a note, no question). Whoever makes a card is the leader by default, which writes nothing on the card.

- **The buttons**: round buttons at the left of the pilots of the Flight section (and of the Pilots table of the MDC format) and at the left of the flights of the package (Package table, the roll call of the MDC); the pressed one is filled (solid blue), the others are rings. They are HTML in `#seatov` over the canvas, placed from the cell boxes (`boxOf`), kept between redraws (so a change of state runs the CSS transition) and never drawn into the canvas: the kneeboard and the exports stay clean. The text of those cells starts after the button, in the canvas too (`ind` in `mdcText` and in the generic branch of the datacard in `cardview.js`, so the name indent is in the kneeboard exports as well); the size of the button and of that indent are computed in one place, `core/seatgeo.js` (`seatBtn`, `seatIndent`, `seatCell`: the button is 0.8 of the height of the cell between 22 and 32 canvas px, 6 px from the left edge, 8 px before the text). `seatDraw()` is called at the end of `ST.hlDraw` (every draw and resize). A seat without an aircraft, and a flight of the package that has no card or belongs to a mission of another flight, are disabled with the reason in the title. The layout of the buttons in the real card is a design choice made with the pilot, not a rule of the code.
- **A seat chosen**: the name of the pilot is written in the Name cell as a manual change (a mission keeps it): the name of the Logbook with the rank of the roster ("Maj. Chris", `seatMe()`), the callsign (Squadron > Me) only when the Logbook has no name, taken off the other seats (the campaign's name comes back where the seat was given up, `giveBack`); a pilot of the squadron roster already on the seat is asked first (`rosterPilot`); the same button gives the seat up. A name that is not on the roster is a pilot of the campaign and is replaced without a question. Choosing a flight writes the callsign again in the new flight (`seatEnter`, after the manual changes are back).
- **What follows from the seat**: the laser code (below), the B. CODE cells, and in the MDC the IFF (M2, M3: `fl<i>_m` = "mode 2|mode 3", a hidden key written per aircraft by `applyDTC0`, saved in missions) and the Link 16 STN of the aircraft (`core/mdcfill.js` `mdcDerive(F, seat)`, called by `mdcAuto()` with `seatIdx()`). The datacard and the MDC take the codes of the aircraft from the DTC of the pilot and the IFF file of the campaign.
- **IFF and Link 16 in the DTC**: once the pilot has chosen a seat (`ST.SEAT.set`; the default, the leader, writes nothing) the DTC takes the codes of that aircraft, and giving the seat up writes the leader's values back (as the laser code does). `core/iffseat.js` holds the rules (pure, `tests/run-iffseat.mjs`): in a Mode 2 or Mode 3 code the low six bits are a block (4, 24 or 44) + 4 x the flight of the package + the aircraft of the flight, the high bits stay; `iffSeatEdits` gives the lines of `[IFF]` that change (Mode 2 code, Mode 3A code and the Mode 3A code of every `TIME n` event; not Mode 1 or Mode 4); the lines of `[LINK16]` are in the next bullet. `app/seatdtc.js` writes them (`seatDtcPush` = `S` + `dtcChanged` + the Data Cartridge page drawn again); only the lines that change are written, and a code that is not one of this flight (typed by hand, or the DTC of another flight) is left alone. `seatToDtc(groups)` in `seat.js` runs on every seat event (`seatRefresh`, `seatEnter`, a mission opened). The groups `iff` and `l16` are two more switches "from Datacard" (the Status card of IFF and the File A card of Link 16; `DCS0`, `SYNC` of the page, `dtcprefs.json`, on by default; `dcSync` writes the seat's values when one is switched on). `app/dtcapply.js` derives the codes of each aircraft with the same `seatIffCode`, so rewriting a code and reading it back give the same codes and the card and the DTC never fight. Not checked in the real game: the values are those of the campaign's IFF pattern and of the sample Link 16 file.
- **Link 16 in the DTC** (`core/l16plan.js`, pure, `tests/run-l16plan.mjs`; `app/l16link.js` is the part that reads the card and writes the DTC): a DTC has two files, A and B, each with the callsign (two letters: the first and the last of the callsign, "Cobra" CA, "Falcon" FN), the number (the flight digit of the callsign and the position of the aircraft: Cobra 3, seat 1 = `31`), the flight lead flag (1 only for the leader) and 16 STN slots (0-3 `FLIGHT_1..4`, 4-7 `TEAM_1..4`, 8-15 `DONOR_1..8`; the value is 5 octal digits, the STN of the flight (4 digits, from the campaign's `.l16.txtpb`) + the position, `00000` = empty). **File A is the plan of BMS** (`autoPlan`): the own flight from slot 1, every other flight of the package, in the order of the datacard, from the first slot of the next block of four (two 2-ships are 1-2 and 5-6; three full flights are 1-8 and donors 1-4). The flights come from the package table of the card (`pk<i>_0` callsign, `_1` aircraft, `_4` STN), so it works for a mission too (no campaign file there). **File B is empty** and the program does not touch it until the pilot puts something in it. **The changes of the pilot are records** tied to the flight, not to slot numbers: `{k:'put', a, cs, stn, n, s, m}` (a flight put at slot `s`, `m` = 'l' leader only or 'a' all its aircraft), `{k:'off', a, cs}` (a flight taken out of the plan) and `{k:'pin', a, s, v}` (an STN typed by hand: the slot stays as typed, the plan goes on around it); `resolvePlan` applies them in the order made over the plan (A) or over an empty file (B). **A flight is always put in or taken out whole**: a flight a change touches loses all its slots (leader only over a full donor flight empties its other three; a flight already in the file moves; a shorter flight over a longer one empties the extra slots), and the own flight cannot be added or taken out; Team goes in slots 5-8, donors in 9-16 (`placeCheck`, otherwise nothing is written). The records are `ST.L16OV` (flight key -> records), kept when another flight is on the card, cleared with the card (`manClear`) and saved in the mission (`datacard.l16`, `l16Save/l16Load`). **When it is written**: with a seat chosen (`seatToDtc`, group `l16`: the plan, the callsign letters, the number and the flag, only the lines that change) and at once on a change of the pilot (`l16Add/l16Remove/l16Unpin/l16Back` -> `push`); it needs the switch "from Datacard" of the File A card, a DTC with `[LINK16]` and an own flight with an STN (`l16Can()` says why not). Choosing a seat writes the whole plan of file A again: what the pilot had set in BMS (donors) is replaced. The changes are made from two places: **the map** (a click on a flight of the package opens a small window, "Select flight" / "Add Link 16": file A or B, Team or Donor, only the leader or the whole flight, the first slot (a menu with what is in each slot; the default is where the flight is now, else the first free run), and the lines of what changes (`startOptions`, `defaultStart`, `diffLines`), Remove; `member()`/`matePopup()` in `mapview.js`, the descriptor of a flight from the ATO entry, `l16Mate`) and **the Link 16 page of the Data Cartridge** (a chip beside each STN with the flight and the position: grey = the plan, blue = put by the pilot, amber = typed; a cross on the first slot of each flight (not the own one) takes it out, "Back to auto" (A) / "Clear" (B) take every change back; an STN typed by hand becomes a `pin`, unless it is what the plan has there; `dtcChanged` -> `l16Typed`). With the editing of the map off (Weapons pages) a click on a flight only selects it, as before.
- **Channels and radio presets in the DTC** (`app/flightdtc.js`, `core/radioplan.js`, `tests/run-radioplan.mjs`): whatever the seat, `seatEnter` (after a card is built) and the switches "from Datacard" of Link 16 (`l16`) and of the Radio page (`radio`) write the channels of the flight (`l16ChanEdits` in `app/l16link.js`: Mission, Fighter, Special of file A from `dl0_mc` / `dl0_fc` / `dl0_sc`, 000 = none) and the presets 5, 6, 13, 15 of `[Radio]` (UHF) and 5, 6, 13, 15-19 (VHF) from the card (`radioPlan(F)`: 6 own flight, 13 first tanker, 5 AWACS, UHF 15 UHF2 of the first flight, VHF 15+ the flights of the package). Hidden card keys (`XD`): `dl0_sc`, `rd_u15`, `su<i>_v`. Only the lines that change and exist in the file; the notes are BMS's. The IFF codes are not calculated (BMS makes them): the page only says they are the ones saved.
- **Places on the map**: `PLACE_LAYERS` (`core/mapconst.js`: cities 8, towns 28, villages 29 = the types of `OBJ_TYPES`) are drawn by the same `objDraw` as the objectives (`OBJ_ALL` in `core/mapview.js`), but they are the "Political" block of the side panel of the Objects (own rows, own political button), are not part of the Objects switches / the all-none button, have a dot class `pl1..pl3` (size) and no buildings (no `featLoad`, no zoom: a click opens the window). `mapUnits` gives `telar` for the classes with slot 0 (radar in every launcher).
- Tests of the Link 16 plan: `tests/run-l16plan.mjs` (the rules), `tools/l16-test.py` (the DTC per seat for a package of four flights, the changes, file B, the page, the window of the map, the mission); `window.__app.l16` is for the tests.
- **Laser**: the TGP code of the DTC is the CONF-LSR code of the seat. `datacard.js` mirrors `fl<i>_5` <-> `LaserTGP` in the group `lsr` (switch "from Datacard" of the Laser card of the DTC page, on by default, remembered in `dtcprefs.json`); `mir(..., when)` has a predicate so only the seat's row takes part (`seatIdx() === i`). The LST code and the start time stay in the DTC. B. CODE 1 / 2 are a reference of the datacard (default: the CONF-LSR of the seat, may be typed over), not a DTC value (`seatCodes()`).
- **Missions**: `datacard.seat = { n, set, uid }` is saved (`seatSave`); on opening, `seatResolve` (end of `msfLoad`) restores the seat of whoever saved it (same `uid`), gives the leader to an own mission from before the seat existed, and for a mission of another pilot looks for his own name on the card, else neutral with the buttons lit (`.ask`) and a line under the card; the laser code of the DTC is pushed only when the DTC block of the mission was applied. `msfSig`, the snapshots and `unsaved()` include the seat. A change of the file shape is a new field only: older readers ignore it (`MIN_READER` stays).
- **Package buttons**: `goFlight(k)` opens the card of another flight of the package (`CAM.els0` gives the elements in the order of the Package rows; `flightOf` finds the index in `ST.CL`); the changes of the card that no mission holds are asked about first (`unsaved()`).
- **Name cell**: a click on a Name cell opens the standard menu (`#chm`: Auto, Type a name, the roster; `openNameMenu` in `editor.js`); the pilot list of the Flight section has the same style (`#pnmenu`, `style-02.css`).
- Tests: `tools/seat-test.py` (the buttons and their place, the names, the laser, IFF / Link 16 in the MDC and in the DTC, the flights and missions, the standard menu, the animations), `tools/dtcpage-test.py` (the Laser, IFF and Link 16 switches), `tests/run-mdcfill.mjs` (the seat arguments of `mdcDerive`), `tests/run-iffseat.mjs` (IFF per seat, the geometry of the buttons). `window.__app.seat` and `__app.cellRect(k)` are for the tests.

## Docs page

`app/js/core/docspage.js` (`createDocsPage(deps)`, the PDF reading is handed in as `deps.pdf`). The viewer shows one page at a time, or (switch **Scroll**, off at the first start, remembered in `localStorage['bmsdocscroll']`) all the pages one below the other: a slot for every page (sized from the page; the sizes of the pages after the first are read in the background and the place in the document is kept), a page is drawn only while it is near the view and freed when it is far (a serial queue, at most 36 million pixels per page); the page in view is the current page (number box, arrows, thumbnail), so "Add page to cards" adds that one; the zoom applies to all the pages; the arrows, the thumbnails and the number box scroll to the page (smooth only with the animations on). **All pages** asks first above `ALL_WARN` (20) pages, then adds them with a strip under the toolbar (where it is, a bar, Cancel); opening another document stops the run. The thumbnails stay when the view is drawn again. Tests: `tools/docs-test.py` (with `SHOTS=<folder>` it saves screenshots).

## State and settings

- `ST` (`app/js/app/state.js`) holds what several modules assign. Settings: `config.json` next to the exe (desktop) or the browser storage; remembered choices (last DTC / campaign) live under `ui` in the config.
- Small files (`savePrefs`, `savePrefsSafe` in `platform/desktop.js`) are written 800 ms after the last change; when the window closes, `flushAll()` writes what still waits (a page that keeps a change waiting hands it over with `beforeClose`).
- The program is portable: its files are next to the exe. At start a small file is written there and removed (`canWriteAppDir`); a folder that cannot be written (Program Files, read-only) is said once, and so is the first file of the program that cannot be saved (`onSaveFail` / `saveFailed`, `checkAppFolder` in `app/settings.js`). The web view keeps its own data in `data\webview` only when that folder can be written (`src-tauri/src/main.rs`), otherwise in the user's folder, so the program starts anyway. The Settings name the folders typed that do not exist before saving.
- The map keeps its own choices (layers, filters, menus) in `store` (`core/mapconst.js`).

## Settings window and moving the data

- `app/js/app/settings.js` builds the window (`<dialog id="cfg">`; every class starts with `s-` and is written under `#cfg` in `css/style-10.css`): the sections on the left, the page of the chosen one on the right, Cancel / Save in the footer. **Essentials**: Folders (the five folders, each with a status: found, automatic, not found) and Diagnostics (`settingsdiag.js`: version, the program folder and whether it can be written, the game data that was read, a full report that opens in place). **Preferences**: General, Datacard, Mission & squadron, Map. **Data**: Import & backup (`settingsdata.js`). The pieces shared by the pages (icons, chips, the switch row) are in `settingsui.js`.
- A section with a changed value has a dot (`OF` compares each section with the values at opening). Save is enabled only then, does not close the window and says "Saved"; the switches and the boxes are applied on Save. The page is built when the window opens and not before.
- The CSP (`script-src 'self'`) allows no inline handler: the window reacts to `data-a` attributes (one delegated handler in `settings.js`: `go close save sw report step browse`, one in `settingsdata.js`: `pickfolder pickfile back dismiss pick pol start restart export again`; the names must not collide, a button closed with the name of the other handler closes the window).
- **Import from another version**: the pilot chooses the program folder of an older copy or a backup file (`.zip`). `core/transferrun.js` reads and writes (the file access is handed in as `io`, so the same code runs in the program and in the tests), `core/transfer.js` holds the rules (no file access) and `core/zip.js` reads (store and deflate, CRC-32 checked) and writes (store only) the zip. It is a copy: the older folder is never written. The items: Settings (`config.json`: a folder that does not exist on this computer is not taken; a file equal to the defaults counts as not customised), Page preferences (`mapprefs`, `perfprefs`, `dtcprefs`, `dtcdefaults`, `mfddefault`), Squadrons (`squadron.json`, with the pilot identity; an empty one counts as nothing), Missions (a folder each), Kneeboard (`cardmemory`) and the Backups of the originals (`backup\dtc`, `backup\kneeboard`; an original already kept here is never overwritten). What exists in both places follows the policy: "Use imported" (default: what is replaced is first copied to `backup\before-import-<day>`) or "Keep mine".
- After an import only the files that were written are frozen (`freezeFiles` in `platform/desktop.js`, `kbMemFreeze`): the program cannot write the old values over them before it is started again. The window says so and has a "Restart now" button (`flushAll()` and a reload). The data of the web view (`data\webview`: the browser storage and the database of the 16K map) is not part of the move.
- A missions folder of the older copy that lies inside its program folder is not shared: `insidePath` (transfer.js) makes the imported path automatic and the missions are copied; a copy already tied to the older folder is put back to its own in the same run (`runImport`, before the copy of the missions).
- **Export my data** writes the same items into one zip (`saveFileBytes`, the manifest `bms-cards-backup.json` names the format and the version of the program); temporary files and the safety copies of an import are left out. The permission to write a `.zip` is in `src-tauri/capabilities/default.json` (`tests/run-capabilities.mjs` checks every file the program writes against it).
- Tests: `tests/run-zip.mjs` and `tests/run-transfer.mjs` (rules, on a file system in memory: `tests/memfs.mjs`), `tools/settings-test.py` (the window) and `tools/import-test.py` (the whole move on the data of a real 1.0.0: `tools/v10data.py` makes it with the code of the tag `v1.0.0`, `V10_CACHE=<file>` keeps it between runs). Browser tests of the desktop part use `tools/fakedesk.py` / `fakedesk.js`: a Windows-like file system in memory that enforces the permissions of the capability file (a write that is not allowed fails as in the real program) and answers scripted file dialogs. The real Tauri window is not tested in the sandbox: check it on a real PC.

## Conventions

- Formatting: Prettier (`npm run format`); lint: ESLint (`npm run lint`: no errors, no warnings).
- Animations: see the rule below. Tests run with reduced motion unless they test an animation.
- Big pages are one closure on purpose (`createMap` in mapview.js, squadron.js, weaponspage.js): their inner functions share state. Do not cut them without a feature that needs it.

## Big files (terrain, 16K map)

- Every call of `platform/desktop.js` to the file system is an exchange with the Rust side (open, seek, read and close are four of them), so reads are grouped: `readRanges` opens a file once for several pieces read side by side; `heightsAt` (`bmsdata/heightmap.js`) reads the whole row of the height map (about 64 KB) when a row is asked for twice or more, and keeps it in `createRowCache` (64 MB, least recently used first; one for each terrain in `app/gamefiles.js`). Whatever needs heights of the terrain (MSA, radar coverage, DTC target heights, airbase elevations) asks `heightsOf(terrain, points)` of `app/gamefiles.js`, so the rows are shared. Test: `tests/run-heightmap.mjs`, `tools/terrain-test.py`.
- The BMS folder picture (16K, 100+ MB) is not read at start: `deps.localMapInfo()` (`app/pages.js`) gives its name and size (together they are the signature of the saved copies) and `read()`, called only when the picture has to be decoded. `core/skylayer.js` is the map layer; `core/skypic.js` holds what does not need the browser (levels, `BlockStore`, `picDb`, `buildBlocks`, `reduceInSlices`, `TileCache`; `tests/run-skypic.mjs`). In the program's database (`idb` of `mapconst.js`, store `blobs`, keys `sky|<signature>|...`) are the reduced copy (4096 px) and the blocks of 2048 px; a picture of 12,288 px or more has two levels (the picture and its half), a smaller one only the picture; two pictures are kept at most, the least recently used goes with its blocks. The manifest is written first as unfinished and last as finished, so a picture that was not completed is cut again and its blocks can still be removed. The blocks are JPEG at quality 1: below 1 the browser keeps half of the colour resolution (4:2:0) and thin coloured lines of a chart are washed out (`tools/skypic-test.py` checks it), at 1 it keeps all of it.
- A tile is drawn from the level whose pixels are still sharp for its zoom (`pickLevel`: the reduced copy down to zoom 9 on a 16K picture, the half level at 10, the picture from 11), from the blocks that are decoded (at most 384 MB, least recently used first; the others are read from the database and decoded when a tile needs them). A tile whose blocks are not there is drawn at once from the reduced copy and drawn again in place when they are; a part over two blocks is put together at 1:1 before it is drawn (drawn block by block it shows a faint line at the join). Tiles that leave the screen are kept for the way back (`TileCache`, 320). The mesh of a tile is `meshFor(zoom)` (error under 0.15 px). A block that is missing or cannot be decoded makes the program cut the blocks again, once. Test: `tools/mapcache-test.py` (the file is read once, never again; sharp tiles; a block gone; a full database), `tools/skypic-test.py`.

## Animations (rule: always)

Every function or button that is added comes with its animation, in the same change; a feature without it is not finished.

- **Buttons and fields**: a hover and a press change that is animated. `.btn`, `.seg button`, `.tab`, `.dsw`, `.wex`, `.nst button` already have 0.15 s transitions and a press (`:active`, `scale(.97)`); a new kind of button copies them. Text fields and selects get the border and ring transition from `style-01.css` (written with `:where()`, so a field with its own look keeps it). A clickable row lights up under the pointer.
- **Appearing**: a menu, panel or pop-up shown with `display`, `hidden` or the `hide` class fades in by itself (`app/js/app/appear.js`), and so does whatever is added straight to `<body>` and the content under a `.wtabs` bar when another tab is chosen. An element shown by a class of an ancestor (`body.onwp ...`) has `animation: appear .15s ease-out` in CSS (`appear` has only the `from` step, so a dimmed button ends dimmed). Folding: `expand()` / `collapse()` (`app/js/app/base.js`) or, in CSS only, `grid-template-rows: 0fr` to `1fr` (the enemy block `.wen` of the BVR timeline: closed it is `visibility: hidden`, so Tab cannot reach it).
- **Changing**: change a class on the same element, so the CSS transition has a "before"; an element that is drawn again has none (the yellow row of the BVR table, the highlight of the Data Cartridge menu, the arrow that turns). A glyph that turns is one glyph in a `span`, rotated by a class. When a page has to be drawn again anyway (the Sliders switch and the kt | Mach buttons of the BVR page), the new switch is put back in its old state, a style flush is forced (`void el.offsetWidth`) and then the new state is set, so the transition still runs (`flip()` in `core/missilespage.js`).
- **Not everywhere**: results that a slider redraws many times a second are not faded (they would blink: the MSA bands and labels of the map, the BVR table and drawing while a slider moves). Fade what appears because of a deliberate choice (a page tab, another row, a hovered airbase).
- **Off switches**: `.noanim` (Settings > Animations) and `prefers-reduced-motion` stop every CSS transition and animation (`style-08.css`), so write the animation in CSS whenever possible: it obeys them without code. A script animation (Web Animations API) asks `animOn()` first.
- **Settings window**: the page of a section fades in (`sxin`), the switches slide, the dot of a changed section grows, the full report and the own satellite layer open in place (`.s-xp`: the height follows the content, like the enemy block of the BVR page), the arrow turns, the progress bar grows, the check pops (`sxpop`) and the lines of a result come in one after the other. All of it is CSS, so both off switches stop it.
- **Seat buttons and the Docs viewer**: the round buttons over the card change with a transition (the dot grows, the row lights up, the line under the card fades) and the ones that ask for a choice pulse (`seatask`); the canvas of a page of the Docs viewer fades in (`dcfade`), the strip of "All pages" opens and closes (Web Animations API, asked `anim()` first) and its bar grows; the arrows of the viewer scroll smoothly only with the animations on. `tools/seat-test.py` and `tools/docs-test.py` check them and the off switches.
- **Test**: `tools/animations-test.py` visits every tab and every page of the Settings window and fails when a visible button, tab, select, link or text field has no transition; it also checks the animations above (the Settings ones too) and both off switches, and `tools/import-test.py` does the same check on the views of Import and Export. Add the check of a new animation there.

## Squadron (online)

- Pilots find each other through WebSocket trackers (only offers and answers pass there) and then talk over a WebRTC data-channel mesh. Everything that travels is a JSON message: the roster, the organization, missions (zip, then base64 in chunks with an acknowledgement) and kneeboard cards (a picture as a `data:` address, at most 8 MB). A message above what a channel carries is split into fragments.
- The state of a squadron (`q`) is kept in `squadron.json` next to the program (`core/prefs.js`: the text is written to `squadron.json.new` and read back, only then to `squadron.json`, so a whole copy always exists; a file that cannot be read is kept as `.bad`, never overwritten by an empty start). The roster merges member by member, the organization item by item: the newer time stamp wins, a deleted package or flight stays as a marker for 60 days so the pilots who were offline hear about it.
- `core/organization.js`: the rules of the organization, pure functions without DOM or network: `q.owner` (commander), `q.mc` (mission commander), `q.org` (packages, flights, seats), `orgView` (what is shown: the limits of 5 flights and 4 pilots are applied there, the same on every computer), `orgReduce` (every action of the board with its permission check), templates.
- `core/orgpage.js`: the board as HTML and its events (clicks, menus, dragging with pointer events: the HTML5 drag-and-drop does not reach the page inside the Tauri window on Windows). `core/squadron.js`: the page itself (network, persistence, Me / Members / Organization / Missions / Settings).
- Every change has a time stamp from `orgClock` (the clock of the computer, never before the newest change already seen), so a late clock cannot make a new change lose. The wait for the answer to a mission or card is an idle timeout (`ackWait`): it starts again at every piece sent.
- The members of a squadron are trusted: the roles are rules of the screen and of the shared data, not a defence against a hostile member (decided, see `ROADMAP.md`).
- Tests: `tests/run-organization.mjs` (rules), `run-swarm.mjs` (transport, rosters, cards; no BMS file, runs in CI), `run-squadron.mjs` (logbook cipher, needs a campaign file), `tools/squadron-test.py` (the whole page, with a simulated mesh) and `tools/squadron-scale-test.py` (many pilots).

## Tests

- `npm run check` = lint + format check + types + `npm test` (what the CI runs on every push, on a clean clone).
- Types: `// @ts-check` at the top of a file puts it under `tsc` (`npm run typecheck`, files listed in `tsconfig.json`); the pure modules (parsers, rules, mapdtc, mapdata, popup, lethal, strike, coalitions) are in. Add a file to `tsconfig.json` when it is typed.
- `npm test`: `tests/run-all.mjs` runs every `tests/run-*.mjs`; a test whose BMS files are missing is skipped with a note (list `NEEDS` in the runner). Chain (parsers, golden flights, ATO, map data, popup / strike / lethality maths, DTC campaign `.ini` format ...). Tests that need BMS data are skipped when `BMS_DATA` is not set.
- `python3 tools/run-all.py [-j N] [name ...]`: all browser tests, two at a time, a failed one is repeated alone. Each test has its own port. About 30 minutes sequentially.
- Text that comes from outside (campaign and theater files, mission files, other pilots) is always put in the page through `esc()` (or `textContent`); numbers of the DTC (slots, ranges, 100 weapon targets) come from `GROUPS`, `STPT_RANGE`, `WT_N` in `core/mapdtc.js`; the tested BMS version is `BMS_TESTED` in `core/version.js`; the installed version is read by `bmsdata/exever.js` from `Bin\\x64\\Falcon BMS.exe` (PE headers; the pieces of the exe come from the `read_exe_range` command in `src-tauri/src/main.rs`, because the file plugin does not open executables) and compared at start in `app/gamedata.js`.
- After editing code: `npm run format`, `npm run lint`, `npm test`, then the browser tests of the page touched.
